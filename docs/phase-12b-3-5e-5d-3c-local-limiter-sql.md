## Objects and transaction guarantees

Migration `20261014000000_partner_logo_verification_limiter.sql` creates private schema verification_private, singleton configuration and global_lock tables, admin_locks, admissions and leases, their constraints/indexes, and public admission/release RPCs. No JWT, Storage path, filename or Partner content is stored. UUID identities and timestamps are the only request data. Admissions persist indefinitely, including after membership removal; lease ownership is enforced by a composite FK. No membership FK deletes replay history.

Both RPCs are VOLATILE SECURITY DEFINER with empty search_path and qualified object references. Both reject isolation other than READ COMMITTED. Admission locks global → administrator; release locks global → administrator → lease. All counts run in later statements after lock acquisition, using one clock_timestamp captured after locks. READ COMMITTED plus volatile statement snapshots lets a waiter observe earlier committed admissions. Global row serialization prevents rate/concurrency check-write races and serializes administrator lock creation. Missing singleton configuration/lock fails with an exception. Exceptions, lock timeout and transaction rollback do not produce admission success. No retries are implemented.

Window is `(now - 60 seconds, now]` for server-created history; exact lower boundary excluded. Rate counts successful admissions even if leases were released; concurrency counts unreleased leases with expires_at > now. Successful admission and lease insert together. Expiration frees concurrency capacity but never confirms release or cancels upstream work. A later deployment must ensure upstream deadlines and cancellation fit TTL; otherwise expired workers can overlap newly admitted work.

Configuration seed is LOCAL ONLY: admin/global budgets 10/100, concurrency 1/10, fixed 60-second window, TTL candidate 30 seconds. Not approved for production. Administrative configuration changes must take the global row lock first, then update configuration in the same transaction. Runtime clients receive no configuration write privileges.

## Contracts and invocation trust boundary

Both SQL RPCs return one scalar JSONB result, not SETOF. The current SQL result is explicitly UNVERSIONED: there is no version field. Fixture assertions require exact keys and reject an unexpected version; a future versioned adapter contract needs separate review. This SQL contract is distinct from the existing verification response version/invariants, which remain unchanged.

Admission `(request_id, admin_id, session_id)` returns exactly one JSONB object:

- admitted: request_id, lease_id, admin_id, session_id, admitted_at, expires_at, plus status.
- replay: status and request_id only; never a new grant, never permission to inspect metadata.
- membership-denied, ownership-denied, rate-limited, concurrency-limited: status only.

Membership is checked after global locking before administrator row creation and again after administrator locking. Cross-identity replay of successful requests is denied; a revoked original admin receives membership-denied before replay. Session validity and identity provenance cannot be established from UUID arguments. The future server invoker must cryptographically verify authentication/session and supply the verified UUIDs itself. Browser UUIDs are not authority. Current membership uses public.cms_admins and requires a reviewed owner with legitimate visibility through existing RLS.

Individual denial decisions are not persisted, so a previously denied request ID may later be evaluated and admitted. Denials do not add admission/lease rows. Administrator locks grow per distinct verified member identity, not per denied request; non-member arbitrary UUIDs and unknown releases do not create locks. There is no automatic purge: deleting admission history would allow request replay, and retention/recovery needs separate review. Storage grows with successful admissions and historic administrators.

Release `(request_id, lease_id, admin_id, session_id)` validates all identifiers together. Unknown lease returns unknown; known lease with any mismatched identifier returns ownership-denied. Identity-matched released/already-released/expired results echo all four UUIDs. No current membership required. A previously confirmed release remains already-released even after its TTL expires. An unreleased expired lease remains expired and is never marked released.

Future adapter mapping: released and already-released succeed only after exact tuple and response-shape verification. expired, unknown, ownership-denied, ambiguous/unavailable, malformed/unexpected result, replay or lost acknowledgment are errors and block metadata. Expiration alone cannot prove successful release; a worker may still be running. No hidden retry on any unknown outcome. Caller must await transaction commit, not merely receive an RPC row in an open transaction.

## Privileges and owner prerequisite — execution deliberately disabled

Existing migrations inherit their execution role; they do not establish a dedicated safe definer owner. Functions inherit the actual migration execution owner. This migration creates no roles and grants no BYPASSRLS; it does not assert that the inherited owner is approved for operational use. All schema/table privileges are revoked from PUBLIC, anon, authenticated and service_role. RPC EXECUTE is revoked from those same roles, including any default Supabase grants. Owner retains implicit privileges. No service_role EXECUTE grant is present: deployment needs a separate reviewed ownership/grant migration. Empty search_path is not a substitute for ownership review.

After the revocations and before COMMIT, a DO precondition inspects actual proowner values, recursively traverses every API role membership edge irrespective of SET/INHERIT options, rejects reachable superuser/CREATEROLE/ADMIN OPTION powers, reachable owner or EXECUTE access, private schema ownership/USAGE/CREATE, private table ownership/access, and any PUBLIC ACL entry on the new objects. Effective has_*_privilege checks include inherited/default grants that survive direct revocation. Missing API roles abort. The conservative traversal can reject harmless disabled membership edges; this is intentional fail-closed behavior, not an exact role-switch emulator.

These checks do NOT prove that arbitrary existing SECURITY DEFINER functions, external credentials, administrative actors or concurrent role changes cannot regrant privileges or switch identity. Accordingly a second, unconditional DO block raises SQLSTATE 42501 before COMMIT even if all local checks succeed. The entire creation/revocation transaction rolls back; a runner must stop on errors. No GUC, runtime flag, role-name allowlist or request parameter bypasses this gate. The authored migration CANNOT complete as written. Only a future separately authorized, reviewed source change can remove the final gate after catalog/security review; do not skip blocks or remove the gate just to run tests.

Before any application or gate-removal review, inspect pg_proc.proowner/proacl/prosecdef/provolatile/proconfig; pg_namespace.nspowner/nspacl; pg_class.relowner/relacl/relrowsecurity/relforcerowsecurity; pg_roles.rolsuper/rolbypassrls/rolcanlogin/rolinherit; pg_auth_members and recursively effective memberships; pg_default_acl; pg_policy on cms_admins; and pg_catalog.has_*_privilege for all API roles including inherited grants and PUBLIC ACL entries. Check both complete signatures, configuration/lock seed rows and all indexes/constraints. Test owner membership visibility rather than assuming SELECT bypasses RLS.

A preferred dedicated NOLOGIN, NOSUPERUSER, NOBYPASSRLS owner would need narrowly scoped limiter privileges and existing-policy-compatible membership visibility. The current cms_admins policy does not authorize such a dedicated owner to enumerate verified UUIDs. Therefore safe ownership cannot be resolved here without a separately approved policy/ownership design. Do not change existing CMS grants/policies in this phase. An existing cms_admins table owner can bypass its ordinary RLS; a superuser/platform migration owner has broader powers. Either choice carries a documented privilege escalation trade-off and requires explicit security review before any EXECUTE grant, not an implicit deployment assumption. A dedicated role must not become reachable through API-role membership or login.

Once verified and approved, grant EXECUTE only to the intended server invoker (candidate service_role) on these two signatures; no direct private-table/schema usage is needed by a SECURITY DEFINER invoker. Verify anon/authenticated/PUBLIC remain unable to execute and roles cannot acquire the owner. Service-role credentials permit broad platform access: compromise can spoof UUIDs, consume budgets or call unrelated APIs. Keep credentials server-only, authenticate every request, and do not treat limiter RPCs as a replacement for that boundary.

Private schema must remain absent from Supabase/PostgREST exposed schemas; inspect effective deployment configuration, not only repository config. No exposed-schema configuration changed. Other powerful database owners/operators are outside the browser privilege boundary and must not mutate limiter state outside the locking protocol.
